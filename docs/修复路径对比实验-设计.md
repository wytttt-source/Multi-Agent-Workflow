## 1. 为什么必须先修一个缺陷（P0-6）

**现象**：局部重规划（`replan_local`）回到执行节点时，`subtasks` 没变，`build_query(st)`
生成的检索式与首轮**完全一致**；而 `search_with_evidence` 的缓存键含 query，
于是第二轮直接命中首轮的磁盘/内存缓存 —— "重试"没有带来任何新证据。

**证据**（v2.2 实跑，`比较Python和Java在并发编程与内存管理上`）：

```
-> [检索] 主查询 '... lang:zh'
-> [缓存] 命中磁盘缓存（6 条）        ← 第二轮与首轮同 query
-> [反思] 子任务覆盖率仅 50%
```

这正是 E4/E5 里"同类型错误反复重规划、空转到上限"的机制来源：
P0-5 当年只修了自由反思那一侧（`_build_retry_query`），局部修复这一侧没修。

**修法**：`executor_node` 在 `replan_count > 0` 时改用 `_retry_query_for()` 生成检索式
（默认 `missing_term`：主题 + 未覆盖对象；另有 `drop_lang` / `same` 对照），
并把 `search.retry_query / retry_mode / retry_round` 落盘。

**口径影响**：这是一个**缺陷修复，不是实验臂**，四臂同享。修订只改变
「重规划是否带来新证据」，不改变判定标准；受影响的是历史上出现过局部重规划的组
（E4/E5），因此 v2.3 需要重跑这 8 份记录，旧记录保留不动。

## 2. 四臂定义（唯一变量 = `REPAIR_POLICY`）

| 臂 | 环境变量 | 路径规则 | 回答的问题 |
|---|---|---|---|
| **B0** | `ENABLE_REFLECTION=0` | 不判、不修，直接判通过 | 不修能拿到多少（下界） |
| **F** | `REPAIR_POLICY=fixed` | 只按错误类型做固定映射：内容不合格→局部、分解不合理→全局；**不允许自由反思**（判断不清就局部重试） | "只按分类修"够不够 |
| **R** | `REPAIR_POLICY=free` | 一律补检索 + 重写，**不做定向修复** | "不看依据、只换检索式"够不够 |
| **H** | `REPAIR_POLICY=hybrid` | 有确定性依据→定向（局部/全局）；判断不清→自由反思（v2.2 默认） | 混合是否优于任一极端 |

实现位置：
- `agents/nodes.py::_decide_next` 先算「这条错误**需要**哪种修复」（`desired`），
  再经 `_apply_repair_policy()` 得到「策略**允许**走哪条」（`path`），写入 `state.repair_path`；
- `main.py::route_after_reflection` **只认 `repair_path`**，不再用 `error_type` 猜——
  否则 fixed 臂的「证据不足」会被误送去自由反思（路由与策略打架）。

四臂共用同一份判定代码，因此**三态分布只可能因"修得怎么样"而变，不会因"判得宽严"而变**。

## 3. 12 道题与首轮受控注入

注入只在 `replan_count == 0` 生效（`INJECT_FAULT`）；修复轮次看到的是真实生成结果，
否则注入会把每一轮都打断，实验退化为"永远修不好"。

| 组 | 题号 | 注入 | 想要触发 | 必答对象 |
|---|---|---|---|---|
| A 检索缺口 | A1–A4 | `one_side` | 首轮只拿到单侧证据 → 覆盖率不足 | 2 个对象 |
| B 结构缺陷 | B1–B4 | `one_side` | 三对象题只讲一个 → 分解不合理 | 3 个对象 |
| C 内容缺陷 | C1/C4 | `truncate` | 停在连接词 → 确定性截断规则 | 见任务集 |
| C 内容缺陷 | C2 | `short` | 正文 60 字 → 字数门 | 3 个术语 |
| C 内容缺陷 | C3 | `no_cite` | 砍掉【来源】→ 降级救援 | 1 个对象 |

任务定义（含 `required_objects` / `requires_citation` / 注入理由）见
`experiments/tasks_repair.json`。**C3 是刻意保留的反例**：无引用会被降级救援改判
「降级通过」并直接结束，修复路径根本没有机会介入 —— 案例集里专门用它说明
"救援与修复会互相抢戏"。

注入形态都取自真实坏样本，不是随机破坏：过短、缺引用、半截话、单侧证据，
四者都能被现有门控确定性识别，因此"修没修好"有客观判据。

> `one_side` 的实现是**首轮只检索第一个对象**，不是"检索完再裁掉一半结果"。
> 后者实跑会被证伪：对比类文章几乎都会同时提到两个对象，"只提到 Python"的结果几乎不存在，
> 裁剪要么全留、要么退化成前 2 条，注入变成空操作（P-B0 首轮直接判通过就是这种假阴性）。

## 4. 判卷口径（与系统判定相互独立）

`experiments/evaluate_answers.py::judge()`：

1. **否决**：必答对象缺项 / 正文 < 120 字 / 命中截断规则 / 出现不可核验 URL；
2. **降级**：以上都过，但该题要求引用而答案没写可核验引用；
3. **合格**：其余。

与系统终态比对得到三类误判：
- `误放行`：系统判通过、判卷不合格（最严重）；
- `误否决`：系统判否决、判卷合格；
- `粒度错位`：通过/降级/否决之间错位（只影响三态统计，不影响二分类）。

**为什么判卷要看必答对象**：v2 的 `content_gate` 只看字数/引用/截断，
"补上了引用、却只讲了一个对象"能一路通过。这一维是 v2.3 唯一新增的判定事实，
用来暴露 R 臂最常见的退化形态。

## 5. 指标

| 指标 | 定义 | 回答什么 |
|---|---|---|
| 修复率 | `outcome=fixed` / 首轮失败数 | 修得回来吗 |
| 无效重试率 | `outcome=failed 且 replan>0` / 该臂总数 | 白跑了多少 |
| 判卷合格率 | `rubric=pass` / 该臂总数 | 最终答对多少 |
| 误判率 | 系统终态 ≠ 判卷 / 该臂总数 | 判得准不准 |
| 独占合格题数 | 只有该臂合格的题数 | **该路径是否不可替代** |
| 成本 | `repair.cost`：`llm_calls` / `searches` / `elapsed_s` | 代价多大 |

`repair.outcome` 四态（`nodes._repair_outcome`）：
`pass_first_try` / `fixed` / `partial` / `degraded_unchanged` / `failed`。
其中 `degraded_unchanged` 单列，避免把"首轮降级、终轮还降级"错算成修复失败。

## 6. 协议

1. **温度归零**：`LLM_TEMPERATURE=0`，消除生成抖动对"路径选择"这一被解释变量的干扰；
2. **轮次上限**：`REPAIR_MAX_ROUNDS=3`（与 v2.2 一致，不因实验放宽）；
3. **目录隔离**：`RUN_RECORD_DIR=data/runs_v3`，臂 = `EXP_GROUP=P-B0|P-F|P-R|P-H`；
   v2 的 `data/runs_v2/` 只读，**任何表格不得与 v3 合并**；
4. **配对**：同一题在四臂下各跑一次（12×4=48），按题配对比较，不做跨题平均的显著性声明；
5. **预跑筛题**：先跑 H 臂，若某题首轮即通过（`pass_first_try`）则记为"注入未生效"，
   重跑该题或换注入；不能把"没触发缺陷"的样本算进修复率分母；
6. **重跑规则**：同一 (臂, 题) 只保留一份记录；重跑前先删旧 JSON（或 `--skip-existing`）。

## 7. 复现命令

```powershell
# 0) 干跑：确认 48 条命令与 env
python experiments/repair_matrix.py --dry-run
```

## 8. 效度威胁（写论文时必须交代）

1. **注入是受控污染**：四类缺陷都由脚本注入，只能做**机制归因**
   （"这种坏法，哪条路能修"），不能外推真实缺陷分布；
2. **样本量小**：12 题 × 4 臂，足够做配对描述统计，不足以支撑显著性检验；
3. **单模型单语言**：生成 deepseek-flash / 裁判 glm-5.3-flash，全部中文任务；
4. **检索缓存**：首轮结果可能来自磁盘缓存，注入已经绕开了缓存差异（注入在生成之后）；
5. **网络抖动**：实跑中出现过 GLM 超时导致单轮耗时 190 秒，故表 1 的耗时只作参考，
   成本结论以 `llm_calls` 为主；
6. **C3 类样本（无引用）**：降级救援会抢在修复之前结束流程，不能用来比较修复路径。
