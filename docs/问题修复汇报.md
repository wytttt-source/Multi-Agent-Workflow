## 1. 第一批 P0：判定语义漏洞（「可读」被当成了「可信」）

**统一症状**：几处口子通向同一个后果 —— 无来源 / 无引用的回答被判 `通过` 并计入合格样本。

**为什么必须一起改**：门控只覆盖「裁判 LLM 正常返回」这一条路径；裁判故障（P0-3）与自由反思收尾（P0-4）各自有一条「直接判通过」的短路，不经过门控。三条路径必须同时收口，否则「降级率」会因为走了哪条路而抖动。

### P0-1 无引用回答被判「通过」（`has_source_line` 算了不用）

- **问题**：`content_gate` 明明算出了 `has_source_line=False`，但 `_apply_pass_gate` 的否决链只读 `evidence_nonempty` / `no_fabricated_url` / `len_ok`，三项全过 → 判 `通过`。
- **根因**：字段有产出、无消费者；判定链少一档「格式服从 ≠ 资料支撑」。
- **怎么解决**：在否决链中插入一档：`not has_source_line or cited_count < PASS_MIN_CITED` → `降级通过`，`hit = 无引用支撑`；`reason` 里写清「【来源】=有/无、可核验引用 N 条 < 门槛」，便于逐条复查。
- **验收**：`ContentGateTest.test_c1_no_source_line_is_not_pass`；离线 6 组对照（无来源无 URL：`通过`→`降级通过`；引用 1 条合法 URL：`通过`→`通过`，`pass_kind=strict`）。

### P0-2 资料支撑度没有门槛（1 条证据即达标）

- **问题**：只有「证据非空」这一个二元条件，没有「回答引用了几条」的概念 —— 模型只要写一行【来源】就能蒙过。
- **怎么解决**：`content_gate` 增 `cited_count`（命中来源清单的 URL 数）、`cited_loose`（截断引用单列）、`citation_ratio = cited_count / min(来源数, EVIDENCE_TOP_K)`；新增 `PASS_MIN_CITED=1`。
- **关键教训（差点把「严」做成「错」）**：首版只做精确字符串比对，结果把真实可核验的回答判死 —— 模型把 `.../visitnodedetail?courseId=200901994&knowledgeId=116677997` 截断成 `.../visitnodedetail` 后引用，被判「编造 URL」→ `内容不合格` + 一次无谓重规划。**修法**：`_verified_kind()` 分两级 —— `exact`（完全一致）/ `prefix`（来源 URL 的前缀，且必须在路径边界 `?` 或 `/` 处截断，防止 `a.com/x` 蒙成 `a.com/xyz`）；只写域名根（`https://a.com`）仍判不可核验（首页不算「引用了某条来源」）。
- **验收**：`test_c2`（有引用判通过）、`test_c3`（编造 URL 拒绝）、`test_c3b`（截断引用判可核验）、`test_domain_root_only_is_not_verified`、`test_url_normalization_anchor_and_trailing_punct`；实跑同一主题：改前 `replan=1`，改后 `replan=0` 且 `cited_count=3`、`citation_ratio=1.0`。

### P0-3 规则兜底「有证据即通过」

- **问题**：裁判 LLM 故障时走 `rule_based_reflection`，旧逻辑是「正文 ≥ 20 字 + 证据非空」→ 直接 `通过`（实测 `{'error_type':'通过','gated_by':'rule_fallback'}`，而回答里一条引用都没有）。
- **怎么解决**：兜底路径不再自带判定，改为复用 `_apply_pass_gate`（与主路径同一套否决链）；未过则 `降级通过`，`gated_by` 记 `gate`，`reason` 注明「规则兜底 + 无引用」；v2.2 起 20 字门槛也统一按 `_body_chars()` 计。
- **验收**：`test_c4_rule_fallback_without_citation_is_degraded`（负例）+ `test_rule_fallback_with_citation_passes`（正例，防止兜底把合格样本误伤）。

### P0-4 自由反思「补到资料即通过」，完全绕过门控

- **问题**：`free_reflection_node` 收尾写的是 `final_error_type = "降级通过" if used_fallback else "通过"` —— 不看字数、不看来源、不看引用；补检索成功的短答案也计合格。而且它自己拼 `run_stats`，容易与终端判定不一致（JSON 一套、日志一套）。
- **怎么解决**：补检索成功后同样跑 `content_gate` + `_apply_pass_gate`，未过则 `降级通过` 并记 `pass_kind="degraded"`；v2.2 再叠加 `_apply_degrade_rescue()`；`_merge_reflection()` 统一写 `verdict / gated_by / decision_source / pass_kind` 与全部门控事实字段。
- **验收**：`test_c5_free_reflection_success_without_citation_is_degraded` + `test_c5b_..._with_citation_passes`。

### P0-5 补检索用同一条 query → 命中同一份磁盘缓存

- **问题**：`search_with_evidence(topic)` 内部固定 `build_query(topic)`，缓存键含 query → 同参数必然同键，「补检索」等于读上一次的结果；更糟的是空结果也曾被当成有效缓存，等于永久救不回来。
- **怎么解决**：① `search_with_evidence(topic, query="")` 支持显式检索式，内存缓存键加入 query；② 新增 `RETRY_QUERY_MODE` 三档：`missing_term`（默认，主题 + 未覆盖对象）、`drop_lang`（去掉语言限定）、`same`（对照组，故意不改写）；③ 实际取式落 `run_stats.search.retry_query` / `retry_mode`；④ 空结果不写缓存，命中空缓存则丢弃并重新联网。
- **验收**：`test_c6_retry_query_differs_from_first_round`、`test_retry_mode_same_keeps_original_query`；24 份记录里 2 条发生过补检索（E4/E5 的 Zig/Nim），`retry_mode` 可逐条核对。

## 2. 第二批 P1：规则信号与阈值（「规则给了信号，但信号是坏的」）

### P1-1 重复检测只对 `分解不合理` 生效 → 空转到上限

- **问题**：`repeat_hit` 只写在 `if error_type == "分解不合理"` 分支里；`内容不合格` 连发 3 次仍然走局部重规划，用同一条 query 打同一批证据，最后撞 `replan_count ≤ 3` 上限。
- **怎么解决**：把重复检测提到所有分支之前 —— **任意类型第 2 次出现即转 `证据不足`**，交给自由反思换检索式；`ENABLE_REPEAT_RULE=False` 可回到旧行为（E5 消融）；`repeat_hit` 落盘便于统计。
- **验收**：`test_c8_second_content_failure_goes_free_reflection`、`test_first_occurrence_still_replans_locally`（第一次仍走局部，不能一刀切）、`test_e5_repeat_rule_can_be_disabled`、`test_repeat_hit_recorded_in_run_stats`；E4/E5 各 1 条降级 + 1 条空转，与 README §3.1 一致。

### P1-2 覆盖率 term 切分脆弱（规则永远命中不了）

- **问题**：`Python和Java的并发性能` 被切成 `["Python", "Java的并发"]`；`对比Kafka与RabbitMQ在吞吐上的表现` 被切成 `["Kafka", "RabbitMQ在吞吐上的表现"]` —— 这些 term 在证据里当然找不到字面，覆盖率恒 < 100%，于是**正常回答被误判分解不合理**。
- **怎么解决**：三层清洗 `_clean_term()`：疑问尾巴（`哪个/如何/怎么…`）→ 状语段（`在…上的表现`）→ 框架后缀（`的?并发?性能|区别|差异|特点…`）；命中判定改 `_norm_text()`（去空白 + 小写）；另设 `_clean_for_coverage()` 只服务覆盖率，**不用于检索词**（否则 query 变短、召回下降）。
- **验收**：`CoverageTermTest` 6 条（其中 5 条属于 P1-2：`test_p1_2_suffix_and_question_tails`、`test_composite_terms`、`test_hit_is_case_and_space_insensitive` 等；第 6 条属于 P1-3）；边界用例与一次真实误判记录在 [`覆盖率的边界用例.md`](覆盖率的边界用例.md)。

### P1-3 `balance` 只统计标题 → 误判「偏侧」

- **问题**：`balance`（最弱一侧命中条数 / 总条数）原来只数标题；很多真实证据的标题是「XX 官方文档」这种泛标题，对象名只出现在摘要里 → 被判成偏侧，进而误判。
- **怎么解决**：改成「标题 + 摘要前 300 字」联合统计；`per_term_counts` 一并喂给裁判，让语义判断也有数字可看。
- **验收**：`test_p1_3_balance_uses_summary_not_only_title`。

### P1-4 空磁盘缓存冒充 `disk`

- **问题**：磁盘缓存读到空串时仍标记 `cache="disk"`，随后真实联网；事后统计「省没省网络」全错。
- **怎么解决**：只有**非空**磁盘命中才写 `disk`；联网成功 `network`、必应兜底 `bing`、同进程命中 `memory`；新增 `cache_source` 字段并让 `run_stats.search.cache_sources` 只读它（`cache` 保留兼容）。
- **验收**：`SearchCacheStatsTest`（v2.1 的 A2 又补了「内存命中只改 `cache`、没改 `cache_source`」这一半）。

### P1-5 阈值硬编码，实验无法调参

- **问题**：120 字下限、3 条证据上限写死在函数体里，想跑消融只能改代码。
- **怎么解决**：`PASS_MIN_CHARS`、`EVIDENCE_TOP_K`、`PASS_MIN_CITED` 进 `config.py`，支持环境变量覆盖，**默认值不变**；`citation_ratio` 分子超过门槛时压到 `1.0`（原始条数看 `cited_count`）。
- **验收**：`ExperimentSwitchTest`；`run_matrix.py` 用环境变量切组，零改代码。

## 4. 第四批 v2.1：口径与实现对齐（"文档说的和代码做的不是一回事"）

### A1 裁判自报 `检索失败` 与内部标签不一致 → 重复检测恒失效

- **问题**：裁判自报 `检索失败`，历史里按 `证据不足` 落盘，但匹配时又去找 `[检索失败]` 前缀 → 同类失败连发时 `repeat_hit` 永远是假，重复检测形同不存在。
- **怎么解决**：新增 `_norm_type()`，**存储与匹配共用同一标签**（`检索失败 → 证据不足`）；历史里保留 `原判检索失败：…` 以便追溯裁判原始措辞。
- **验收**：`test_c9_retrieval_failure_label_normalized_for_repeat`。

### A2 内存缓存命中只改 `cache`，没改 `cache_source`

- **问题**：同进程二次检索命中内存缓存，只写 `cache="memory"`，`cache_source` 还是首次的 `disk`/`network` → `cache_sources` 统计把「省了网络」算成「走了网络」。
- **怎么解决**：两个字段同时改写。
- **验收**：`test_memory_hit_reports_memory_cache_source`。

### C1 字数门按**全文**计，被【来源】行注水（规则列的最大缺口）

- **问题**：样本 S05 —— 正文只有 60 字，但【来源】里塞了长标题，全文 154 字，旧口径判 `通过`。这不是「规则不够严」，是**统计口径错了**：来源清单不是回答内容。
- **怎么解决**：新增 `_body_chars()`（剔除【来源】及其后全部内容、剔除整行只有 URL 的行），`len_ok` 改按正文计；落盘新增 `body_chars` / `len_full`，让「正文 vs 全文」可对照。
- **验收**：`test_s05_source_line_padding_does_not_count_as_body`；规则列准确率 **89% → 94%**（缺口只剩 S14 偏题）；24 份记录**零翻转**（最短的合格样本正文 124 字，仍高于 120）。

### C2 `prompts.py` 硬编码 120，与 `PASS_MIN_CHARS` 脱钩

- **问题**：改了配置，裁判看到的提示词还是「少于 120 字」→ 判据与阈值不一致，消融实验失效。
- **怎么解决**：prompt 改占位符 `{min_chars}`，由 `config.PASS_MIN_CHARS` 注入；默认 120，行为不变。
- **验收**：`REFLECTION_PROMPT.format(...)` 两处（反思节点 + 兜底路径）均传参；默认值下 24 份记录零翻转。

## 5. 第五批 v2.2：双向门控（「只会否决的闸门，把降级档挤掉了」）

**背景**：v2.1 之后审计发现 4 点诉求里 #1（重复检测归一）、#3（字数按正文计）已修，**#2（判定只单向、降级档丢失）与 #4（完整性没有判定）只做了一半**。本批补齐这两项，并补一条引用率门槛。

### B1 门控只会「否决」→ 三态里的「降级」档在对照实验里丢失

- **问题**：`_apply_pass_gate` 开头就是 `if error_type != "通过": return ...` —— 裁判判「内容不合格 / 检索失败」的样本，即使回答**可读、只是没拿外部资料 / 已如实声明兜底**，也一律记成否决。结果 C 列 5 条真值 `降级通过` 全部被记成 `否决`，其中 4 条属于可救援类型（S01 未引用来源、S10 无资料兜底、S11 无资料兜底、S16 声明式兜底）。
- **怎么解决**：新增 `_apply_degrade_rescue()`，三条规则按优先级匹配（都只依赖可复现事实）：
  - **R1 声明式兜底**：回答里 `【声明】` 提到「未获取到 / 无法获取 / 未检索到 / 基于模型内部知识 / 模型知识兜底」→ 如实交代不该按「胡说」记否决；
  - **R2 无资料兜底**：`used_fallback=True` 或证据 0 条 → 基于模型内部知识；
  - **R3 未引用来源**：有证据、可读、`cited_count=0`，且 `_answer_on_topic()` 粗判「确实在讲这个主题」→ 可读但没写可核验引用。
  - **前置门槛**：正文够长（`len_ok`）+ 无编造 URL + 未截断，三者缺一不救；**永不改判为 `通过`**（只到 `降级通过`）。
  - **落盘**：`rescued_from`（从哪个否决类型救回）+ `rescue_rule`（凭哪条规则），台账可追溯。
- **验收**：`DegradeRescueTest` 6 条 —— R1/R2/R3 三条正例 + **R3b 偏题不救** + **R4 编造 URL 不救** + **R5 开关关闭回到单向闸门**；`gate_vs_llm --mock` 后 C 列三态 **5/0/13 → 5/4/9**，R/L/C 二分类指标 **94%/89%/100% 不变**（README §3.2 第 3 点）。

### B2 没有完整性判定 → 半截话也算合格

- **问题**：只要正文够 120 字、引用可核验，哪怕结尾停在「以及」或括号没闭合，仍然判 `通过`。
- **怎么解决**：`utils._looks_truncated()` 只认**确定性能判定**的形态：① 正文结尾停在分隔符（`，、；：…`）；② 停在连接词（`以及/和/与/等/包括…`）；③ 括号不配对（含中英文圆括号、【】、『』、书名号、引号）。命中即判 `内容不合格`（`hit=回答截断`），命中项写 `truncation_hits`。开关 `ENABLE_TRUNCATION_RULE`。
- **边界**：「以句号收尾但话没说完」的语义截断**不**在范围内 —— 交给 120 字下限与语义裁判兜住，论文里不要写成「全覆盖」。
- **验收**：`TruncationTest` 4 条（结尾分隔符 / 括号不配对 / 正常回答不误伤 / 开关关闭回 v2.1 行为）；24 份真实回答 `truncated` 命中 **0/20**（零误伤，见 [`反思归因表.md`](反思归因表.md) 第 6 节）。

### B3 引用率只记录不判定

- **问题**：`citation_ratio` 从 v2.0 起就落盘了，但没有任何门限读它 —— 一个「记录了却不用」的指标。
- **怎么解决**：新增 `PASS_MIN_CITATION_RATIO`，默认 `0`（**不判定**，保持 v2.1 行为）；设成 `0.5` 后，`cited_count / min(来源数, EVIDENCE_TOP_K) < 0.5` 判 `降级通过`（`hit=引用率不足`）。分母封顶 `EVIDENCE_TOP_K`，因为「检索给 6 条、只引用 3 条」不算违规。
- **验收**：`CitationRatioTest` 2 条（门槛生效降级 / 默认 0 不影响任何判定）；默认值下 24 份记录零翻转。

### B4 「裁判没跑」与「裁判跑了没剔」在记录里无法区分

- **问题**：检索层三层过滤里，GLM 裁判失败时 fail-safe 保留全部结果；但记录里 `filtered == raw` 既可能是「裁判判断都不相关但都保留」也可能是「裁判压根没跑」，剔除率无法解释。
- **怎么解决**：`llm_relevance_filter(..., stats_out=)` 写回两种形态 —— 成功 `{applied: true, kept, dropped, total}`、失败 `{applied: false, reason, total}`；开关关闭时写 `{applied: false, reason: "disabled"}`；由 `search_with_evidence` 落到 `run_stats.search.llm_filter`（executor 聚合进 `run_stats.search.llm_filter` 列表）。
- **行为不变**：失败仍保留全部结果（fail-safe），只是多留一条痕迹。
- **验收**：`FilterDegradedTest` 2 条（失败被标记 / 成功报告剔除条数）。

### B5 两处 20 字门槛用 `len(全文)`，与门控的「正文」口径再次分叉

- **问题**：C1 把门控改成按正文计字数了，但反思节点里「少于 20 字直接判内容不合格」和规则兜底里的 `length < 20` 还在用 `len(result)` —— 同一个概念两套口径，正是 C1 那类 bug 的复发点。
- **怎么解决**：两处统一改 `_body_chars()`；门控、兜底、救援现在共用同一个正文定义（`_body_text()` 单一来源）。
- **验收**：`grep -n "len(result)"` 无残留；`ReflectionPathTest` 用例覆盖兜底路径。

## 7. 未解决 / 有意保留（出论文数字前必读）

1. **S14 偏题**：规则结构上读不懂「答非所问」，字面信号全合格 → R 列唯一的缺口，也是必须保留 LLM 语义层的直接证据。
2. **S09 只写域名根**：记为 `内容不合格` 而不是 `降级通过`（它与「编造 URL」共用同一个否决档），这是**有意保留的保守口径**（宁可判否决，不可放行）；按「降级率」统计时单列说明，见混淆矩阵 §6 第 9 条。
3. **截断规则不是全覆盖**：`_looks_truncated()` 只认结尾分隔符/连接词与括号不配对，抓不到「以句号收尾但话没说完」；论文里写成「确定性完整性信号」而非「完整性检测」。
4. **救援是单向的**：只把否决改判 `降级通过`，永不改成 `通过`；因此它修正的是三态粒度，不是合格率。反过来，救援也可能把「恰好提到主题词的偏题回答」降级（而非否决），属可接受误差（`_answer_on_topic` 是粗判）。
5. **空转 2/2 不是 bug**：E4/E5 的两条补检索仍拿不到该对象证据，最终由自由反思走模型知识兜底并声明 —— 这是「规则不该被绕过」的正常结局。
6. **temperature=0.1**：裁判仍有抖动，判决器对照文件 repeat=1；要完全可复现需把 `temperature` 降到 0（独立改动项）。
7. **样本量**：判决器对照 n=18（每类陷阱 1 条）、消融 24 份记录 —— 只能说明「这类错能被抓住」，给不出该类错误率。
