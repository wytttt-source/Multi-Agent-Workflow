## 案例 1｜A1 检索缺口：问题在检索式，不在拆解

### ① 任务与注入

- 主题：`比较Python和Java的并发性能`（复合主题，2 个必答对象）
- 注入：`INJECT_FAULT=one_side` → 首轮**只检索第一个对象**（`one_side:first_object:Python`）
- 判卷：正文必须同时出现 `Python` 与 `Java`，且要有可核验引用

### ② 首轮发生了什么

只发了一条查询 `Python并发性能 lang:zh`，证据里没有 Java 相关内容。
裁判按覆盖率规则先判 `分解不合理`（证据覆盖率 50%，未覆盖 `Java`），**没有走到语义裁判**。

### ③ 四臂各自的路径与结果

| 臂 | 路径序列 | 修复结果 | LLM 调用 | 判卷 | 与系统判定 |
|---|---|---|---|---|---|
| B0 无反思 | （不判） | `pass_first_try` | 2 | 通过 | 一致 |
| F 固定类型 | `global → local → local` | **failed（撞上限）** | **9** | 通过 | **误否决** |
| R 自由反思 | `free → 通过` | `fixed` | 4 | 通过 | 一致 |
| H 混合 | `global → free → 通过` | `fixed` | 8 | 通过 | 一致 |

用时：B0 11.5 s / R 210.2 s / H 167.9 s / F 294.6 s（含网络抖动，成本以调用次数为准）。

### ④ 机制解释

- **F 错在路径**：`_REPLAN_TYPES` 把 `分解不合理` 固定映射成"重拆"，可这道题的分解决议没错 ——
  错在检索式只覆盖了一个对象。重拆后子任务变成 `Python并发性能` / `Java并发性能`，
  但覆盖率规则用**子任务字面量**匹配证据，长子任务名几乎不可能原文出现 → 覆盖率恒 0%，
  于是越拆越"不合理"，三轮后撞上限（`failed`）。它的最后一轮答案其实已经覆盖两个对象
  （判卷通过），系统却停在上一轮的 `分解不合理` 上 → 记一次 **误否决**。
- **R 对在"只换检索式"**：`missing_term:Java` 直接把缺的对象塞进查询，一次补检索就修好，只花 4 次调用。
- **H 多花了一倍**：它先按规则走了一次全局重拆（那一步不产生新证据），第二次才转自由反思。
  对"检索缺口"这一类错误，**规则前置反而是过度动作**。
- **B0 没有掉分，但不代表没问题**：模型用参数化知识把 Java 也写了（判卷的字面覆盖满足），
  可引用只来自 Python 侧的证据 —— 判卷只看"正文有没有提到对象"，抓不到"引用与论述对象不匹配"，
  这是当前判卷口径的已知盲区（见 §2 的限制）。

### ⑤ 推广边界

只要"错在检索式覆盖不全"（单侧证据、查询过窄），定向重拆就是无效动作；
此时 R 优于 H，H 优于 F，F 最差（且会误否决）。反过来，若错在"拆解本身"（三对象题只拆两块），
固定映射的 `global` 才是对的 —— 那需要 B 类任务来验证，不能由本案外推。

### ⑥ 复现命令

```powershell
python experiments/repair_matrix.py --tasks A1 --arms B0,F,R,H
python experiments/evaluate_answers.py --stdout
```

## 案例 2｜C1 内容缺陷：截断被"覆盖率"盖住，重写又把正文写短

### ① 任务与注入

- 主题：`深度学习中注意力机制的原理与作用`
- 注入：`INJECT_FAULT=truncate` → 首轮答案被截到 60%（结尾补 `，以及`），命中确定性截断规则
- 判卷：正文必须提到 `注意力`、≥120 字、未截断、引用可核验

### ② 首轮发生了什么

首轮答案确实被截断（记录 `injected=["truncate"]`）。但判定顺序是
**覆盖率前置 → 语义裁判 → 确定性门控**，覆盖率规则先判了 `分解不合理`
（子任务 `深度学习中注意力机制的原理` 未在证据里原文出现），
**截断这个真正的原因根本没被读到**。

### ③ 四臂各自的路径与结果

| 臂 | 路径序列 | 修复结果 | LLM 调用 | 判卷 | 与系统判定 |
|---|---|---|---|---|---|
| B0 无反思 | （不判） | `pass_first_try` | 2 | **否决**（含不可核验 URL） | **误放行** |
| F 固定类型 | `global → local → local` | **failed（撞上限）** | 8 | 通过 | **误否决** |
| R 自由反思 | `free → 通过` | `fixed` | 4 | 通过（正文 123 字 / 引用 3） | 一致 |
| H 混合 | `global → free → 内容不合格` | **failed** | 6 | 否决（正文 94 字） | 一致 |

### ④ 机制解释

- **判定顺序决定归因，归因决定路径**：首轮被当成"结构错"，于是 F 走重拆、H 先走重拆；
  真正需要的是"重新生成一段完整的回答"，而这条只有 R 一开始就走对了。
- **H 的口径没有错，但它没救回来**：第二轮回退自由反思（`path=free`），
  补检索成功，可是重写后的正文只有 94 字（低于 120 字下限），被门控判 `内容不合格` → 撞上限。
  也就是说：**自由反思不是"重写就一定更好"**，它会把长答案改短（这是 R 臂的失败形态之一）。
- **F 的误否决来自覆盖率规则的字面匹配**：子任务名太长，原文不可能逐字出现，
  覆盖率恒 0% → 每轮都判 `分解不合理`，可最后一轮答案其实合格（引用 5 条、正文达标）。
- **B0 的误放行最典型**：不判就等于把截断/不可核验 URL 全部放过，而它只花 2 次调用、183 秒 ——
  "省下来的成本"正是风险所在。

### ⑤ 推广边界

内容缺陷（截断/过短/编造来源）应当**直接重新生成**，而不是重拆；
但重写必须带长度与完整性约束，否则 R 臂会出现"越改越短"。
判定顺序（覆盖率 > 语义 > 门控）会让内容缺陷被结构缺陷掩盖，这一点需要单独在论文里说明。

### ⑥ 复现命令

```powershell
python experiments/repair_matrix.py --tasks C1 --arms B0,F,R,H
python experiments/evaluate_answers.py --stdout
```

## 案例 3｜机制案：局部修复"重试了但没换式"（P0-6）

### ① 现象（v2.2）

`比较Python和Java在并发编程与内存管理上` 的日志：

```
-> [检索] 主查询 '... lang:zh'
-> [缓存] 命中磁盘缓存（6 条）      ← 第二轮与首轮同 query
-> [反思] 子任务覆盖率仅 50%
```

局部重规划时 `subtasks` 不变 → `build_query(st)` 不变 → 缓存键（含 query）不变 →
第二轮拿到的就是第一轮那批证据，"修复"等于空转。P0-5 当年只修了自由反思那一侧
（`_build_retry_query`），局部这一侧漏了。

### ② 修法

`executor_node` 在 `replan_count > 0` 时改用 `_retry_query_for()`：
默认 `missing_term`（子任务 + 未覆盖对象），另有 `drop_lang` / `same`（对照）；
并在 `search.retry_query / retry_mode / retry_round` 落盘，论文里能逐条核对。

### ③ 修复后的实际检索记录（F 臂，A1）

| 顺序 | query | 策略 | 缓存来源 |
|---|---|---|---|
| 首轮（注入） | `Python并发性能 lang:zh` | — | network |
| 第 1 次修复 | `Python并发性能 最新进展 官方文档 lang:zh` | `extra_terms` | **network** |
| 第 2 次修复 | `Java并发性能 Python并发性能 lang:zh` | `missing_term:Python并发性能` | **network** |

两次修复都是真实联网（`cache_source=network`），**不再命中首轮缓存**。

### ④ 为什么 F 还是失败了

修完检索式以后，F 臂卡住的原因变了：不是"没新证据"，而是**覆盖率规则的字面匹配**
（子任务 `Python并发性能` 在证据原文里不逐字出现 → 覆盖率恒 0% → 每轮都判 `分解不合理`）。
这两件事必须分开说，否则会把"检索缺陷"和"判定口径缺陷"混为一谈。

### ⑤ 影响范围与重跑结论

- 这是**缺陷修复，不是实验臂**：四臂同享，因此四臂之间的差异只来自 `REPAIR_POLICY`；
- 历史上出现过局部重规划的记录只有 E4/E5（各 4 份，共 8 份），
  其余 16 份从未进入局部重规划，判定不受影响 → v2.3 只需重跑这 8 份；
- v2 记录（`data/runs_v2/`）保持只读，不与 v3 混表。

### ⑥ 复现命令

```powershell
# 看某份记录到底换了什么检索式
python -c "import json,glob;r=json.load(open(glob.glob('data/runs_v3/P-F/*.json')[0],encoding='utf-8'));print([(q.get('query'),q.get('retry_mode'),q.get('cache_source')) for q in r['search']['per_query']])"

# 对照：强制沿用原 query（会重新命中缓存，用于证明"不换式=空转"）
$env:RETRY_QUERY_MODE='same'; python main.py "比较Python和Java的并发性能"
```

## 口径限制（写论文时必须一起交代）

1. **判卷只看正文覆盖面，不看到底引用了哪一侧的证据**：案例 1 的 B0 用模型知识补上了
   `Java`，判卷就记为"通过"，其实引用全部来自 Python 侧。要抓这一点需要"引用与论述对象
   的匹配度"这一新维度，本版没有做。
2. **覆盖率规则的字面匹配是已知脆弱点**：子任务名过长时覆盖率恒 0%，会把"内容错"
   误判成"结构错"（案例 2 的 F 臂）。这不是 v2.3 引入的，v2.1 起就这么判。
3. **n 小**：案例 1、2 各只有 1 次运行，"R 比 H 省"只在本题成立，
   不能推广成"混合不如纯反思"；结论要等 12 题 × 4 臂的配对表。
4. **耗时不可比**：同一题的耗时在 138~381 秒之间波动（GLM 裁判偶发超时），
   成本结论一律以 `llm_calls` 为准。
